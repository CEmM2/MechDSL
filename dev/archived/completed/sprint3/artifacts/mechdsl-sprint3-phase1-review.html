Sprint 3 Phase 1: Benchmark Hardening

sprint3_phase-1 ← main · +196 lines · 3 files · 0 deletions

The MechDSL compiler pipeline was verified in Sprint 2, but the physical benchmarks used toy meshes with laughably loose tolerances. This phase hardens 3 benchmark test files to production quality: a cantilever beam now runs on a 40×8×4 mesh demanding 5% accuracy, the MMS convergence study uses proper 2× refinement ratios, and a 30° finite rotation test proves frame-indifference of the SVK Total Lagrangian formulation.

Core insight: All changes are purely additive test code. No source modules were touched. The existing tests remain as fast regression gates; the new tests are @e2e @slow gates for nightly CI. This is a risk-free upgrade of verification rigor.

08 Code Review

Good: Purely additive, zero-regression design

All 196 lines are insertions. Existing tests are untouched. Old coarse-mesh cantilever tests remain as fast regression gates. This is textbook benchmark hardening — tighten tolerances without breaking the safety net.

Good: Class-scoped fixture for MMS avoids redundant FEM solves

mms_convergence_results_4level uses scope="class" so the expensive 4-level convergence study (including a 16³ mesh) runs exactly once, shared by both L2 and H1 tests. Matches the existing TestTaskP3T3 pattern.

Good: Physics documentation in docstrings

The 30° rotation test at test_benchmarks.py:326 clearly explains the derivation chain: F=R → C=RTR=I → E=0 → S=0 → fint=0. The tolerance relaxation rationale is documented inline, not hidden in a comment.

Ugly: Tolerance divergence between reference solver and verify harness

test_finite_rotation_30_degrees uses <1e-9 while the equivalent test in test_patch_test.py uses <1e-12. The 3-order gap is documented but may confuse future developers. The root cause (different integration paths in ref_hex8_elastic.py vs verify/patch_test.py) deserves a shared comment or constant.

Ugly: Cantilever fixture defined as instance method inside test class

cantilever_problem_refined at line 553 is a self fixture inside TestCantilever, while the MMS fixture is module-level with scope="class". The inconsistency is inherited from the existing cantilever_problem fixture. Not a bug, but a pattern that will accumulate if Cook's and necking bar follow the same style.

Question: Has the 40×8×4 cantilever been run to completion?

The test is marked @slow and was NOT executed during this phase (only collection was verified). With 12,285 nodes and cg_max_iter=5000 in pure NumPy, the first actual run in CI may reveal convergence issues or timeout. Consider a one-time local validation run before merging.

Question: Will the 16³ MMS mesh complete within nightly budget?

4,913 nodes × 4 mesh levels. The plan allows fallback to [2, 4, 8] if too slow. The test exists but hasn't been timed. Phase 4 CI nightly has a 60-minute budget.

Bad: No CHANGELOG entry for Sprint 3 Phase 1

196 lines of benchmark hardening with no CHANGELOG record. While this is test-only, the benchmark status is a user-facing quality signal. The plan defers CHANGELOG to Phase 5 (P5-4), so this is by design — but worth noting.

09 Decision Log

HIGH CONFIDENCE · sourced from plan + conversation

Keep coarse-mesh cantilever tests alongside refined mesh

Rationale: The 4×2×1 tests run in milliseconds and catch regressions immediately. The 40×8×4 test takes minutes and runs nightly. Both are needed: fast feedback loop + production accuracy.

Alternatives: Replace coarse tests entirely (rejected: loses fast feedback). Parameterize over mesh sizes (rejected: different tolerances make parameterization awkward).

HIGH CONFIDENCE · sourced from plan

Use [2,4,8,16] mesh levels instead of [2,3,4]

Rationale: Proper 2× refinement ratios produce unbiased log-log slope estimates for convergence rate measurement. Non-uniform ratios ([2,3,4] = 1.5× then 1.33×) bias the fit and can mask superconvergence or degradation.

Alternatives: Keep [2,3,4] (rejected: biased rates). Use [4,8,16,32] for finer meshes (rejected: 32³ = 35K nodes is prohibitive in pure NumPy).

MEDIUM CONFIDENCE · inferred from code

Relax 30° rotation tolerance from 1e-12 to 1e-9

Rationale: The reference solver (ref_hex8_elastic.py) accumulates O(1e-10) floating-point roundoff during multi-element Gauss quadrature assembly with steel-like material parameters (MU≈77,000). The verify harness achieves 1e-12 via a different integration path. Tolerance of 1e-9 provides 2 orders of headroom.

Alternatives: Use unit material parameters (rejected: breaks consistency with the TestRigidBodyMotion class which uses steel parameters throughout). Switch to verify harness API (rejected: task spec requires reference solver API).

HIGH CONFIDENCE · sourced from plan

Add @e2e marker at class level on TestTaskP3T5

Rationale: Phase 4 introduces a nightly CI tier collecting -m e2e. Patch test and rigid body tests on irregular mesh must be in that tier. Class-level marker is inherited by all methods, matching the existing @slow pattern.

Alternatives: Method-level markers (rejected: redundant, class already has @slow per-method). No marker, let Phase 4 add it (rejected: Phase 4 expects it done).

10 Re-entry Context

Note from present-you to future-you

Key Invariants

  • The 40×8×4 cantilever test assumes solve_elastic accepts cg_max_iter as a keyword argument. If the solver API changes, this test breaks silently (it would just use the default).
  • TestMMS4LevelConvergence fixture is scope="class" — moving a test method to a different class will re-trigger the expensive solve.
  • The 30° rotation test tolerance (1e-9) is coupled to the reference solver implementation, not the physics. If ref_hex8_elastic.py is improved, the tolerance can be tightened.

Non-obvious Coupling

  • test_benchmarks.py has two independent test scopes on cantilever: the original cantilever_problem fixture (4×2×1) and the new cantilever_problem_refined (40×8×4). They use the same material constants but different meshes. Changing E_YOUNG or NU at module level affects both.
  • Phase 4's CI nightly tier (-m e2e) now collects tests from 3 files. Adding @e2e to more tests increases nightly runtime — budget is 60 minutes.

Gotchas

  • The @e2e @slow tests have NOT been run to completion — only collection was verified. First real execution will be Phase 4's nightly CI or a manual -m slow run.
  • Pre-existing failure: test_analytical.py::test_uniaxial_above_yield_hardening_law fails due to missing scipy dependency. Excluded from fast suite but will appear in full pytest runs.
