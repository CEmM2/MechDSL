07 Risk Assessment

HIGH Golden file regeneration invalidates all codegen tests

Every Phase 1 change modifies emitted Taichi code. Golden files generated_elastic.py.golden and generated_plastic.py.golden will fail until regenerated. Phase 6 must run after Phase 1 completes atomically.

HIGH C2/C5 interaction: quad loop ti.static vs node loops runtime

C2 makes quad loop ti.static while C5 makes most node loops runtime. The GRAD_AT_QUAD gather loop at line 429 must stay ti.static because both q and a must be compile-time for Python list access. Getting this wrong produces a compile error. The other three node loops (416, 446, 476) access ti.Matrix/ti.field/ti.Vector which support runtime indexing.

MEDIUM ReturnMappingResult freezing

H11 changes to frozen=True. Verified 7 importing files — none reassign fields. Numpy arrays inside remain mutable (deferred). Low risk but needs test-suite confirmation.

MEDIUM Tolerance tightening (G1, G4) may reveal latent issues

G1: 1e-2*MU (~769) → 1e-10. For theta=1e-4, SVK forces ~O(theta^2)=O(1e-8), so 1e-10 is achievable. G4: elastic FD tangent 1e-4 → 1e-8. Both aggressive but theoretically correct.

MEDIUM G3: Dirichlet tangent identity changes convergence

Changing Kv[bc_mask] = 0.0 to Kv[bc_mask] = v[bc_mask] in both reference solvers is a functional change. CG convergence may change (likely improve). Apply last in Phase 5 and compare iteration counts.

LOW Missing NaN check in emitted Newton driver

H1 sets dl = NaN on J2 non-convergence. The plan does NOT add a NaN check in the emitted Newton driver. NaN in res_norm causes res_norm < tol to be False, so Newton continues until max_iter. Recommend adding if not np.isfinite(res_norm): raise RuntimeError("NaN in residual").

08 Good / Bad / Ugly

The Good

  • Prioritization: Blocking codegen issues (C1-C5) first, error handling second, tests last. Correct dependency order throughout.
  • Line-number accuracy: 90%+ of cited line numbers verified as correct (minor off-by-2 in a few places).
  • C2 budget rationale: Explains WHY quad loop should be ti.static, calculates unrolled body (~240 lines), confirms within 2000-line kernel budget.
  • Consistent patterns: Emitted Newton driver (C4) matches reference solver pattern. Generated code rises to handwritten safety level.
  • Clear scope control: 5 explicit exclusions with rationale for each deferral.

The Bad

  • T2 underspecified: "May need to carefully craft input" — no concrete test body. Only critical test gap left vague.
  • H4 incomplete: cg_fail_count pattern adds state but plan omits WHERE to initialize it relative to the Newton loop.
  • C4 variable mismatch: Plan uses r_norm but emitted code uses res_norm. Would cause NameError if not corrected.
  • No NaN check in Newton driver: H1 sets NaN but plan doesn't add corresponding NaN detection in emitted driver.

The Ugly

  • C2 contradicts convention: CLAUDE.md lists "quad points q" as mesh index with "Never unroll mesh indices." Making it ti.static is pragmatically correct but creates a documented exception needing 07-CONVENTIONS.md update.
  • C5 inconsistent node loops: Three node loops become runtime but GRAD_AT_QUAD gather stays ti.static. Correct but will confuse future contributors without clear comments.

Open Questions

  • Will freezing ReturnMappingResult break any callers? (Verified: likely no, but needs test confirmation.)
  • Is NaN propagation safe in all Taichi versions? (IEEE 754 says yes, but edge cases possible.)
  • Should 07-CONVENTIONS.md be updated to distinguish element-type constants from mesh indices?
  • H5 sentinel: Does any downstream code compare FLOPS against 0.0? (Likely no — only used for display.)
